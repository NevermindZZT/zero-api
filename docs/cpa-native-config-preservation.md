# CPA 原生配置持久化与升级说明

## 根因与适用范围

已发布的 v1.6.0 及之前版本存在配置覆盖逻辑：zero-api 启动、启动 sidecar、CLI 登录和保存部分设置时，会用数据库中的少量 CPA 字段重新生成整个 CPA YAML。这会删除原生面板维护的路由、模型别名、提供商配置、日志和其他未映射字段；也会把同名字段改回数据库旧值。

这属于 zero-api 的同步逻辑缺陷，并不能仅通过重新挂载 Docker 数据卷解决：文件即使在持久卷里，也可能在启动时被程序覆盖。

**本文对应修复后的源码；v1.6.0 已发布镜像和下载文件不包含本次后续修复。** 未经发布流程更新，拉取同一旧版本不能获得修复。

## 修复后的配置归属

| 配置 | 权威来源与保存规则 |
|---|---|
| CPA 完整配置 | 以 sidecar 数据目录中的 `config.yaml` 为准 |
| 路由、模型别名、提供商配置、流式设置、日志等原生字段 | zero-api 不重建、不丢弃，继续在原生面板管理 |
| host / port / API keys / proxy URL / request retry / debug / allow remote | zero-api 页面读取文件生效值；保存时只合并明确改动的字段 |
| 启用、自动启动 | zero-api 数据库中的进程生命周期设置，不为修改这些开关重写 CPA 文件 |
| Management Key | zero-api DB 保留原始密钥用于管理客户端；现存 YAML 中的密钥或 bcrypt 哈希保持原样，不在启动时重置 |
| auth-dir | 现存原生值保持原样，不被启动模板改回默认目录；首次生成文件时使用默认认证目录的绝对路径 |

注意：如果在原生配置里手动更换 Management Key，需要确保与 zero-api 管理客户端持有的原始密钥一致；仅有 bcrypt 哈希无法还原原始密钥。该修复不会擅自重置原生密钥来掩盖不匹配问题。配置、数据库和认证文件应作为整体备份，而不是只复制 YAML。

## 启动、保存和错误处理

- **启动/重启/升级**：只有配置文件不存在时才生成初始文件；现存有效文件逐字节保留。读取共享字段后再建立管理客户端和启动 sidecar，避免使用过期端点。
- **GET 配置**：读取现存 YAML 和 DB 生命周期信息，不写配置文件。
- **zero-api 页面保存**：前端保存基线，只提交用户实际改变的字段；后端支持部分 PUT，未传字段不清零。这样修改自动启动等开关，不会顺带把原生面板刚改的请求重试或代理地址覆盖掉。
- **显式空值**：有效的 0 次重试、false、空代理字符串和空 API key 数组可以保存；端口必须是 1–65535，负重试次数无效。
- **嵌套字段**：修改 `allow-remote` 不会覆盖 `remote-management` 内的原生密钥、面板仓库或其他选项；YAML 注释、未知配置及继承/别名语义均有回归覆盖。
- **损坏配置**：空文件、非法 YAML、重复键、多文档或不可安全读取的路径会明确报错，不改写成默认文件；准备失败时跳过 CPA 自动启动，不影响主 API 启动。
- **并发边界**：zero-api 内部读写互斥，替换前检查原生文件是否变化；检测到竞争时拒绝并提示刷新。不同进程无法提供跨进程事务保证，不建议在两个面板里同时编辑同一字段；旧客户端若主动提交整个对象，同名字段仍按显式提交处理。

## 自动备份

zero-api 每次真正修改共享字段前，会在同目录保存一份完整的上一版配置：

```text
config.yaml.zero-api.bak
```

默认路径为 `data/cliproxyapi/config.yaml.zero-api.bak`；测试实例则为 `data/dev/cliproxyapi/config.yaml.zero-api.bak`。

- 只保留一份最近的写前备份，不是完整历史记录。
- 重启、只读访问、无实际变化的保存不会覆盖备份。
- 当前文件无效时不会拿它覆盖已有有效备份。
- 新写入配置、临时文件和备份权限为 0600；不要把文件发到公开工单、版本库或聊天中，文件可能包含密钥。
- CPA 原生面板自己的保存不经过这个备份入口。长期恢复仍依赖定期备份整个数据卷。

## 已丢失设置如何恢复

旧版覆盖后，zero-api 数据库只有有限字段，**无法自动重建原生面板中那些已经被删除的配置**。

1. 先停止旧版 zero-api，避免恢复后的文件再次在旧启动逻辑里被覆盖。
2. 私下备份当前数据卷：数据库、CPA 完整配置、认证目录及已有配置备份。不要删除旧卷或 OAuth 文件。
3. 使用包含本修复的新构建；确认持久卷仍挂载到正确数据目录。项目默认 Compose 为 `./data:/app/data`。
4. 若有升级前的完整 YAML、数据卷快照或其他备份，恢复正确配置；若没有，只能在原生面板中重新设置丢失项。不要拿不相关实例的密钥/hash 覆盖现有管理密钥。
5. 先在原生面板核对，再重启 zero-api，对比原生路由/别名等是否保留；只读或重启时配置内容不应因 zero-api 再次改变。CPA 自己可能进行其版本所需的格式迁移，应结合 CPA 日志区分。

本次没有修改或恢复用户的生产配置；本地验证使用临时测试配置，不能据此声称生产环境的旧设置已经找回。

## 验证范围

回归测试覆盖：原生完整 YAML 连续重启保留、共享字段原生修改后读取、部分保存与生命周期-only保存、空值/false/0、未知和嵌套字段、注释和别名、完整私有备份、非法文件不覆盖、启动顺序以及配置刷新并发快照。前端仍需要重新构建并嵌入后端后部署，不是仅重启旧二进制即可获得修复。
